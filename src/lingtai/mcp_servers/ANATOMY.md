# lingtai.mcp_servers

Curated and built-in MCP server package implementations shipped inside the `lingtai` Python distribution. They are launched by catalog/script entry points such as `python -m lingtai.mcp_servers.<name>` and expose real addon tools (IMAP, Telegram, Feishu, WeChat, WhatsApp, Cloud Mail), daemon lifecycle tools, plus bundled progressive-disclosure manuals.

## Components

| File / folder | Role |
|---|---|
| `_skill.py` | Shared bundled-skill helper: re-exports the kernel-owned `split_frontmatter` from `lingtai.kernel._frontmatter` (one impl shared with the prompt-section catalog; kernel never imports the wrapper), `load_skill()` loads package `SKILL.md`, `manual_action_description()` injects frontmatter into the schema, and `manual_payload()` returns the manual body + absolute path without sidecar lists (`_skill.py:36-79`). |
| `_plugin.py` | Curated-MCP **plugin packaging** descriptor: `CuratedMcpPlugin` (`_plugin.py:77-255`) binds package identity, bundled `SKILL.md`, stdio declaration, and reserved `manual`; each descriptor's boolean `settings` opt-in independently delegates SHOW to its bound family provider. Telegram, IMAP, Feishu, WeChat, WhatsApp, and Cloud Mail use that owner-local seam. Declarative only — no discovery, import-by-name, spawning, registration, or config reading; activation/execution/lifecycle stay with the host. |
| `_identity.py` | Shared public-identity envelope/path/write helper for curated messaging MCPs: builds the `lingtai.mcp.identity.v1` document, computes `system/mcp_identities/<name>.json`, and performs the newline-terminated atomic JSON write. Provider-specific account fields and redaction stay in each provider. |
| `_config.py` | Shared env-var → path → strict-JSON config loading sequence for the simple addon loaders; each addon keeps its own public `load_config()` wrapper and return type. WeChat deliberately opts out (two-candidate resolver, status diagnostics, second credentials file). |
| `_entrypoint.py` | The single copy of the stdio entrypoint every curated `__main__.py` used to duplicate: INFO logging to **stderr** so JSON-RPC stdout stays clean, `asyncio.run(serve())`, and a swallowed `KeyboardInterrupt`. |
| `_licc_compat.py` | LICC v1 producer compatibility wrapper. Each server's `<name>/licc.py` shim delegates here, which delegates to the canonical `lingtai.services.mcp_licc` when present and otherwise falls back to writing the same LICC v1 filesystem event shape for standalone or pre-upgrade runtimes. |
| `_results.py` | Shared typed-result builders for the SDK v2 low-level server, which no longer wraps handler return values: `json_tool_result()` builds the canonical `CallToolResult` (JSON text block + `structured_content`, with `is_error` tracking the provider payload's `status`), and `text_resource_result()` builds the single-text-block `ReadResourceResult`. One implementation instead of seven. |
| `local_commands/` | Channel-neutral local messaging command core. It owns the command catalog, Agent dashboard/system reads, established `.refresh`/`.sleep`/`.clear` signal writes, and injected Task Card preference parsing. Provider adapters retain actor admission, command/callback dispatch, localization/rendering, recipient IDs, and transport. |
| `task_card/` | Channel-neutral Task Card cores. `event_projection.py` owns the canonical safe event allowlist, redaction/budgets, API-call grouping, safe result merge, metadata/timestamps, and bounded text rendering. `resident.py` owns `TaskCardRoute` (`account + chat + optional thread`), automatic/programmable slot composition, per-route serialization, commit-after-success, in-place edit, conservative supersession rotation, exact-old delete/missing confirmation, peer adoption, and explicit partial/indeterminate failure outcomes. Provider adapters still own journal I/O, route-specific ID validation/high-water policy, API classification, real edit/delete/send, and persistence. |
| `daemon_common/` | Built-in daemon lifecycle MCP. `daemon_common/server.py` exposes strict LTP-v2 `checkpoint(action='checkpoint', input={state, summary, artifacts?, blocker?, request?}, reasoning)` and `finish(action='finish', input={status, summary?, reason?, artifacts?}, reasoning)`. Checkpoint verifies exact RunDir identity/live state, atomically records sequence/latest and drains bounded ID-bearing parent messages, appends an event/touches heartbeat, then publishes a stable-key nonterminal wake on the singular built-in `daemon` channel (sharing its terminal batch state); a wake failure remains an error but returns the already-drained messages. Finish alone atomically writes `daemon_completion.json` named by `LINGTAI_DAEMON_COMPLETION_FILE`, which runners validate before success. |
| `daemon_email/` | Built-in daemon `email` MCP — the exact `lingtai.tools.email` LTP v2 tool family (unmodified schema/description/dispatch) hosted on a lightweight duck-typed `DaemonEmailAgentShim` (`agent_shim.py`) instead of a live `BaseAgent`, so a daemon subprocess never contends for the parent's workdir lease. Bound to `LINGTAI_AGENT_DIR` (the *parent* agent's own working directory — the daemon's own nested run-dir has no `.agent.json`/heartbeat and cannot pass the mail handshake), so a daemon speaks with the parent's own already-live mailbox address; a daemon, its parent, and any sibling daemon of that same parent are therefore all reachable at that one address. Auto-mounted per task only when `tools` explicitly includes `"email"` (`daemon/__init__.py` `_daemon_email_mcp_registration`/`_with_daemon_email_mcp`), mirroring exactly how `daemon_common` is auto-mounted for `checkpoint` and `finish` — a `tools=[]` result-only daemon never gets this registration. |
| `telegram/`, `imap/`, `feishu/`, `wechat/`, `whatsapp/`, `cloud_mail/` | Curated messaging MCPs. TelegramManager requires an injected `NotificationStorePort`; `telegram/server.py` constructs one POSIX adapter, and handled-mirror policy runs against the current payload in one compare-update so newer mirrors survive (`src/lingtai/mcp_servers/telegram/manager.py:415-425`, `src/lingtai/mcp_servers/telegram/manager.py:1239-1281`, `src/lingtai/mcp_servers/telegram/server.py:660-672`). The external LICC path/envelope and persistent-message lanes remain unchanged. `whatsapp/_family.py` mirrors `telegram/_family.py`'s native LTP-v2 tool family: one strict root envelope (`action`/`input`/`reasoning`/`summarize`) with an action-correlated `input` branch per action, dispatched through `handle_whatsapp()`; `manager.py`'s `SCHEMA`/`ACTIONS` now alias `_family.py`'s, and the manager stays the internal flat action/business boundary behind it. WhatsApp's own twelve actions are declared in `whatsapp/plugin.py`; its descriptor appends owner-bound `settings` and then packaged `manual`. |
| `telegram/plugin.py` | Telegram's plugin descriptor — the reference slice for `_plugin.py`. `TELEGRAM_PLUGIN` states the registry name, server name, summary, homepage, skill name, and explicit settings opt-in; `TELEGRAM_DECLARED_ACTIONS` lists Telegram's own eleven actions with reserved actions deliberately absent, and `TELEGRAM_ACTIONS` is the plugin-composed public list (`telegram/plugin.py:22-40`). `_family.py` builds the schema/dispatch from it, `server.py` its server + profile-manifest identity, and `manager.py` aliases its loaded skill constants. |
| `telegram/settings.py` | Telegram's SHOW-only `SettingRow` provider. It snapshots the exact resolved startup config path, live service-order account authority, startup account values, the manager's import-time cadence, and four hot Task Card values; all six account/config aggregates are marked sensitive before the generic projector serializes them (`telegram/settings.py:15-140`). Missing or non-JSON public truth fails the entire inventory without partial rows. |
| `imap/plugin.py` | IMAP's plugin descriptor, mirroring `telegram/plugin.py`. `IMAP_PLUGIN` states the registry name (`imap`), server name (`lingtai-imap`), summary, homepage, skill name (`imap-mcp-manual`), and its explicit read-only settings opt-in. `IMAP_DECLARED_ACTIONS` remains the fourteen operational actions; generic composition inserts `settings` immediately before `manual`, and `imap/_family.py` supplies the owner provider without changing manager dispatch. |
| `imap/settings.py` | IMAP's SHOW-only provider. `imap_setting_rows()` reads the resolved authority path captured at manager construction plus the running service's complete account snapshot and returns six sensitive five-field rows for config reference, account addresses, credential modes, IMAP/SMTP endpoints, and OAuth configuration. Missing applied truth raises so the generic action returns one fixed no-row failure; no writer or mutation path exists. |
| `feishu/plugin.py` / `feishu/settings.py` | Feishu's descriptor and read-only settings provider. `FEISHU_PLUGIN` opts in; the twelve declared actions omit both reserved names, and composition inserts `settings` immediately before `manual` (`feishu/plugin.py`). The provider reads seven current facts from the bound live service, redacts the configuration reference, app secrets, and sender allowlists through the private row flag, and raises when complete truth is unavailable (`feishu/settings.py`). `_family.py` owns binding and strict dispatch; `server.py` and `manager.py` keep their existing composition roles. |
| `wechat/plugin.py` / `wechat/settings.py` | WeChat's descriptor keeps its nine operational actions separate from the reserved `settings`-before-`manual` pair. The provider projects six five-field rows from the active manager's construction snapshot, redacts the resolved config path, endpoint, allowlist, token, and identity in both displayed value fields, and never rereads or writes owner files. `_family.py` owns the provider binding; `server.py` captures the successfully resolved path and manager values once at startup. |
| `whatsapp/plugin.py`, `whatsapp/settings.py` | WhatsApp's plugin descriptor and read-only settings provider. `WHATSAPP_PLUGIN` opts the family into `settings`; `WHATSAPP_DECLARED_ACTIONS` remains the same twelve personal-account actions, while `WHATSAPP_ACTIONS` inserts `settings` immediately before `manual`. The provider returns seven five-field `SettingRow` values from manager startup facts, privately flags config/path/session/allowlist rows for generic redaction, exposes public `autostart`, and raises when no manager can supply current truth. Focused coverage: `tests/test_whatsapp_settings.py`. |
| `cloud_mail/plugin.py` | Cloud Mail's plugin descriptor opts into two fully redacted rows from `cloud_mail/settings.py`: the exact successfully loaded `config_path` startup snapshot and an opaque `accounts` configured marker (`cloud_mail/plugin.py:20-40`, `cloud_mail/settings.py:1-57`). `CLOUD_MAIL_DECLARED_ACTIONS` still lists only the six business actions; `CLOUD_MAIL_ACTIONS` inserts `settings` immediately before `manual`. The older hand-rolled `cloud_mail/_family.py` keeps its schema/dispatch shape and binds the generic bounded settings child directly; settings input validation precedes provider unavailability, neither reserved action enters the business manager, and operational manager-unavailable behavior stays unchanged. |
| `telegram/render.py` | Converts the model-facing `structured_message` semantic object into Telegram Bot API `InputRichMessage.blocks` and a searchable plain-text preview. It preserves agent-authored wording and emoji while assigning native heading, list, bold-label, code, divider, and footer semantics; `TelegramManager` owns conflict validation and send/reply/edit routing. |
| `telegram/task_card/` | Telegram-owned **adapter + programmable projection** unit (governed component with paired `ANATOMY.md`/`CONTRACT.md` + packaged docs). Its `resident.py` is a compatibility re-export of the shared core; `TelegramManager` supplies compound-ID binding, last-message high-water policy, Telegram error classification, transport, and persistence callbacks. The public `task_card` tool lives in `src/lingtai/tools/task_card/`; Telegram reads the intrinsic artifact and projects it read-only. |
| `feishu/task_card.py` | Feishu-owned resident bindings plus lifecycle workers for the shared automatic event projection and the read-only intrinsic programmable artifact projection. `FeishuManager` supplies account+chat+optional-thread routing, conservative process-local high-water policy, Feishu card transport, and exact resident persistence. |
| `feishu/control_cards.py` | Feishu-owned schema-2.0 renderer and bounded hashed-event claim store for local `/help`, `/status`, `/kanban`, `/system`, `/refresh`, `/sleep`, `/clear`, and `/taskcard` cards. Shared command semantics stay in `local_commands/core.py`; actor admission, routing, callback dispatch, and transport stay in the account/manager adapter. |
| Per-server standard layout | Each curated server package repeats the same file shape: `__init__.py` (package surface), `__main__.py` (`python -m lingtai.mcp_servers.<name>`, delegating to `_entrypoint.py`), `server.py` (the SDK v2 low-level `Server` and its handlers), `manager.py` and/or `_family.py` (the flat action boundary and the LTP-v2 envelope), `account.py`/`client.py`/`service.py` (provider transport and session), `licc.py` (the `_licc_compat.py` shim), and `notification_header.md` (the model-facing "how to read this conversation preview" header the manager injects). Provider extras follow the same rule — `imap/_migrate.py` and `imap/bridge.py`, `cloud_mail/_watermark.py` and `imap/_watermark.py`, `feishu/_errors.py`, `wechat/{api,login,media,types,lockfile}.py`, `whatsapp/{redaction,resources}.py` plus `whatsapp/bridge/` (the Node `whatsapp-web.js` personal-account bridge: `index.js` + `package.json`, spawned and supervised by `whatsapp/client.py`). |
| Per-package `SKILL.md` | The human/agent-facing bundled manual. If a manual has sidecars, the sidecar inventory and relative paths live in this markdown, not in the tool payload. |
| `feishu/reference/` | Packaged operator references for Feishu app permissions/events/card callbacks, complete account config and canary/rollback, safe diagnostic flows, and the Telegram comparison/non-goal matrix. `feishu/SKILL.md` is their progressive-disclosure catalog. |
| `pyproject.toml` package-data entries | Ships every curated MCP `SKILL.md`; `reference/**/*` and `assets/**/*` are also packaged for future sidecar files (`pyproject.toml:175-186`). |

## Connections

- Catalog/script launchers (`pyproject.toml:43-49`) start these servers as subprocess MCPs; agents activate them through the generic MCP capability (`src/lingtai/tools/mcp/ANATOMY.md`).
- Manager schemas include `manual` in each action enum and use `_skill.manual_action_description()` to advertise the bundled skill without loading the full body into the resident schema.
- Telegram, IMAP, Feishu, WeChat, WhatsApp, and Cloud Mail are the six packages wired through `_plugin.py` today. Telegram, IMAP, Feishu, WeChat, and WhatsApp use package descriptors to compose their public schema/dispatch and plugin-owned `manual`; Cloud Mail supplies identity, action, settings schema, and manual facts to its older hand-rolled `cloud_mail/_family.py` through generic descriptor helpers rather than `build_family()`. Each owner opts into settings independently; Telegram binds its provider while preserving the shared SHOW seam. Each server/manager reads its identity or bundled skill constants from its descriptor; all six `manual` actions answer directly from packaged `SKILL.md` and never enter their managers. Settings opt-in remains owner-local: IMAP, Feishu, WeChat, WhatsApp, and Cloud Mail each bind their own provider without creating a cross-addon registry or changing another descriptor. `tests/test_curated_mcp_plugin_package.py` covers generic/Telegram/WeChat packaging invariants; dedicated IMAP, Feishu, WhatsApp, and Cloud Mail curated-plugin tests cover their corresponding descriptors and catalog entries.
- A curated descriptor opts into settings independently by binding one owner provider. Generic composition then inserts strict-empty `settings` immediately before `manual`; provider failure remains one bounded no-row result and ordinary manager actions are unchanged. IMAP's six-row applied-snapshot inventory is covered by `tests/test_imap_settings.py`; Feishu's and WhatsApp's seven-row inventories are covered by `tests/test_feishu_settings.py` and `tests/test_whatsapp_settings.py`; WeChat's six-row inventory is covered by `tests/test_wechat_settings.py`. Cloud Mail's two fully redacted startup-snapshot rows are covered by `tests/test_cloud_mail_addon.py` and `tests/test_cloud_mail_toolfamily_ltpv2.py`.
- Feishu's Agent-facing manual routes operational questions to `feishu/reference/{setup,diagnostics,capability-matrix}.md`. The sidecars ship through the existing package-data glob and deliberately remain absent from the `manual` tool payload.
- Tests pin the manual contract, package-data sidecar support, and Telegram parity in `tests/test_mcp_skill_manuals.py` and `tests/test_telegram_rich_formatting.py`.
- `local_commands/core.py` is injected workdir-bound by each provider's composition root. Telegram's existing renderers preserve their slash-command byte surface; Feishu consumes the same semantic results through `control_cards.py` without depending on Telegram.
- `telegram/_family.py` and `imap/_family.py` each own an independent strict LTP-v2 envelope (`{action, input, reasoning, summarize?}`) built on `lingtai.tools.tool_family.ToolFamily`, with a dependency-free `_basic_validate` dispatch-safety gate that rejects an unknown action, non-string `reasoning`, unknown root field, or cross-branch `input` key before any manager I/O runs. Each manager module keeps its original flat `SCHEMA`/`DESCRIPTION` for the pre-migration per-action description text and `manager.handle()`'s legacy flat-args dispatch, then reassigns the module-level `SCHEMA` name to the family's composed schema (`SCHEMA = _family.TELEGRAM_SCHEMA` / `SCHEMA = _family.IMAP_SCHEMA`) so callers see the strict envelope while the manager's own internal dispatch boundary is unchanged. `tests/test_imap_toolfamily_ltpv2.py` is IMAP's family-specific evidence, mirroring `tests/test_telegram_toolfamily_ltpv2.py`.

## Composition

Parent: `src/lingtai/` wrapper package (`src/lingtai/ANATOMY.md`). Sibling wrapper areas include `agent.py`, `services/`, and `intrinsic_skills/`. Curated MCPs are independent subprocess packages, not intrinsic capabilities.

## State

Cloud Mail's settings provider writes no state. Its manager retains the exact
resolved configuration path loaded at construction, and SHOW projects only
that startup snapshot plus an opaque construction-success marker; it never
reads or traverses the credential-bearing account objects.

The package itself is mostly code + packaged manuals. Runtime state is per-agent and server-specific: e.g. message caches, contacts, inbox replay guards, credential-derived identities, or daemon completion sentinels live under the agent workdir/run dir or `.secrets/`, not in `src/lingtai/mcp_servers/`. The shared manual and identity helpers have no persistent state of their own. Telegram's per-account non-secret `state.json` (under `<workdir>/telegram/<alias>/`) additionally persists the resident Task Card id per chat under a `task_cards` map (`{chat_id: compound_id}`), loaded backward-compatibly and normalized against malformed values by `TelegramAccount._normalize_task_cards`, so the one tracked resident target per account+chat survives a refresh; it is not proof that historical unknown orphan cards do not exist. The same account additionally owns an **ephemeral, non-persisted** per-chat high-water mark of the latest observed Telegram message id (`_last_message_ids`, `telegram/account.py:190`), bumped by every inbound plain message the poll loop sees (`_process_update`) and every outbound `send_message`/`send_photo`/`send_document`, but never by an edit or delete; `_note_chat_message_id`/`get_last_message_id` (`telegram/account.py:1208,1235`) record and expose it, guarded by the same `_state_lock` as `task_cards`. Because Telegram message ids are monotonic per chat this mark is "the chat's last message id"; the manager reads it to keep the resident Task Card residing as the last message (Jason #5272/#5273/#5275). It is deliberately not persisted, so a refresh reports `None` (unknown) until the next observed message, and the manager treats an unknown latest-message mark conservatively by editing in place; malformed or cross-bound resident ids fail loud before transport, and neither condition authorizes deletion. Separately, `TelegramService` owns one current-agent delivery boolean in `<workdir>/telegram/taskcard.json`, loaded with a compatibility default of `True` and written through the kernel atomic JSON primitive with fsync; bound getter/setter callbacks let every configured account's local `/taskcard` command share that one value (`telegram/service.py`, `telegram/account.py`). Feishu persists exact resident bindings in `<workdir>/feishu/task_cards.json` as `account + chat + optional thread` records, Agent-wide enablement/normal-row preferences in `<workdir>/feishu/taskcard.json`, and bounded SHA-256 claims for internal control callbacks in `<workdir>/feishu/control_callbacks.json`. Its last-message high-water is deliberately process-local: after refresh an old persisted card is edited in place until the process observes a later route message, so unknown ordering never authorizes a guessed delete/send.

## Notes

- **Official SDK v2 handler shape (`mcp>=2,<3`, protocol `2026-07-28`).** Every bundled server is a low-level `Server` whose handlers are **constructor parameters** (`on_list_tools`, `on_call_tool`, `on_list_resources`, `on_read_resource`) — the v1 decorators are gone. Each handler is `async (ctx, params) -> <full typed result>`: `params.name`/`params.arguments`/`params.uri` in, `ListToolsResult`/`CallToolResult`/`ListResourcesResult`/`ReadResourceResult` out, built by hand because v2 wraps nothing. Attributes are snake_case (`input_schema`, `mime_type`, `is_error`, `structured_content`). Advertised capabilities are derived from which handlers were registered, so a tool-only server (`cloud_mail`, `daemon_common`) correctly claims no `resources`; none of these servers registers prompts, completion, subscriptions, or multi-round-trip, which is the intended product surface. A provider/domain failure remains a model-readable `CallToolResult(is_error=True)`; an unknown tool name or unknown resource URI is instead a lookup failure, which the 2026-07-28 schema classifies as `InvalidParamsError` — every curated handler raises an official `MCPError` with `code=INVALID_PARAMS` (`-32602`) and `data={"requested": name}` / `data={"uri": uri}` via the shared raisers in `_results.py`. Contract and tests: `src/lingtai/intrinsic_skills/lingtai-kernel-anatomy/reference/mcp-protocol.md`, `tests/test_mcp_sdk_v2_contract.py`.
- **Notification contract:** curated messaging MCPs that change structured notification metadata (`recent_messages`, `latest_incoming`, `referenced_messages`, stable IDs, routing hooks, or preview/body placement) must check `src/lingtai/services/LICC_NOTIFICATION_CONTRACT.md` in the same change.
- **Curated plugin packaging is declarative, not a runtime.** `_plugin.py` adds no in-process plugin runtime, no config flag, and no second registry: a `CuratedMcpPlugin` is a package-local descriptor its own package imports explicitly. `mcp_catalog.json` remains the file the host reads for curated launchers, and `decompress_addons`/activation are untouched — the descriptor is what that catalog entry must agree with, proven by test rather than by generating the file at runtime.
- **Every packaged curated plugin's `manual` action is plugin-owned.** Telegram, IMAP, Feishu, WeChat, and WhatsApp each build their child from their descriptor; Cloud Mail's hand-rolled `build_cloud_mail_family()` always routes `manual` to `CLOUD_MAIL_PLUGIN.manual_payload()` regardless of manager presence. All six answer from packaged `SKILL.md`, retain required root `reasoning` and strict-empty `input`, and never enter their manager; legacy flat manual helpers remain available internally.
- **Manual sidecar minimal contract:** `action="manual"` returns the main `SKILL.md` body, parsed metadata, and the main `SKILL.md` absolute `path` only. Concrete `assets/` and `reference/` lists MUST NOT be returned as structured tool fields; `SKILL.md` is the single source of truth for what sidecars exist and how to follow their relative paths.
- **Packaging discipline:** when adding manual sidecars, put their relative paths in `SKILL.md` and keep the package-data globs for `reference/**/*` / `assets/**/*` so wheels contain them (`pyproject.toml:175-186`).
- **Feishu strict LTP-v2 family:** `feishu/_family.py` owns the public envelope, mirroring `telegram/_family.py`'s split — `feishu_schema()` composes the closed root `{action, input, reasoning, summarize?}` (`action`, `input`, `reasoning` required) with one closed action-owned `input` branch per action (`send`, `check`, `read`, `reply`, `react`, `search`, `delete`, `edit`, `contacts`, `add_contact`, `remove_contact`, `accounts`, `manual`), and `handle_feishu()` is the always-authoritative dispatch gate: it rejects an unsupported root field, unknown/missing `action`, a non-object `input`, a non-string `reasoning`, a non-boolean `summarize`, and any cross-branch `input` key before any `FeishuManager` I/O. `FeishuManager.handle()` stays the internal flat action boundary and now also accepts the LTP-v2 shape directly (detected via `{"input", "reasoning"}.issubset(args)`), re-entering through `_family.handle_feishu` so both call shapes produce identical results; `manager.py`'s own flat `SCHEMA` literal was retired in favor of `SCHEMA = _family.FEISHU_SCHEMA`. Action composition itself is owned by `feishu/plugin.py`'s `FEISHU_PLUGIN`: `FEISHU_DECLARED_ACTIONS` lists Feishu's own twelve actions with `manual` deliberately absent, and `FEISHU_PLUGIN.build_family()` appends the reserved `manual` child, which answers straight from the packaged `SKILL.md` and never reaches `FeishuManager` (see "Every packaged curated plugin's `manual` action is plugin-owned" above) — `FeishuManager._manual()`'s existing flat `manual_payload()` result is unchanged and is byte-identical to what the plugin-owned `manual` child returns, since both alias the same `FEISHU_PLUGIN`-loaded `SKILL.md` copy. Contract and tests: `../tools/tool_family/CONTRACT.md`, `tests/test_feishu_toolfamily_ltpv2.py`, `tests/test_feishu_curated_mcp_plugin_package.py`, `tests/test_mcp_skill_manuals.py`, `tests/test_mcp_sdk_v2_contract.py`.
- **Feishu rich text/post outbound + thread-following reply:** the `send`, `reply`, and `edit` children require exactly one of the legacy plain `text` shortcut or a strict tagged `content` value (`text`, `markdown`, or raw `post` AST). Manager normalization maps that public union to the channel SDK outbound facade; the SDK converter owns Markdown-to-post conversion and safe long-message chunking, while account config keeps `max_attempts=1`. Send/reply results return the primary compound id plus ordered compound chunk ids, and one durable logical sent record retains the exact normalized content and physical chunk projection. `reply` reads the persisted target and defaults `reply_in_thread` from its `thread_id`; explicit booleans override, every chunk of a topic reply stays in-topic, and `reply_target_gone="fail"` forbids a silent fresh-send fallback. `edit` uses the SDK text/post edit path and refreshes the exact persisted sent record only after transport success. `edit`/`delete` are logical-record operations: either the primary or any secondary compound id resolves the whole persisted chunk group, the operation is applied once to every physical member in order, and the result carries the ordered `message_ids`/`chunk_count`/`chunks` projection. A mixed outcome returns `partial_failure` with exact `succeeded_message_ids`/`failed_message_ids` and `automatic_retry_allowed: false` (no implicit whole-group replay), and persists a restart-visible `lifecycle` block plus an `edit_partial`/`delete_partial` status inside the same sent `message.json` without overwriting the prior logical content; `read` projects that `status` and `lifecycle` back to the agent. Public behavior and examples live in `feishu/SKILL.md`; focused coverage lives in `tests/test_feishu_rich_outbound.py`.
- **Feishu media/share/sticker outbound:** `send` and `reply` extend the same strict content union with `image`, `file`, `audio`, `video`, `share_chat`, `share_user`, and `sticker`; media deliberately remains outside `edit` (whose supported set is text/post/card). Media sources are explicit absolute local paths or pre-uploaded provider keys — URLs and relative paths never enter the uploader — and manager normalization maps them to the SDK's upload/reuse shapes. Image/video may carry Markdown captions (wire `post`); file/audio captions remain unsupported. The account's narrow `_SingleAttemptOutboundAdapter` reuses SDK 1.x materialization/upload/chunking but calls `_create`/`_reply` exactly once per chunk, bypassing the SDK's otherwise-unconditional post-to-plaintext downgrade; reply-target and format failures therefore remain failures. If a later physical chunk fails, the account projects the exact earlier provider IDs plus the failed index and original SDK error taxonomy; the manager persists one `status='partial'` logical record, advances route high-water to the last exact success, returns the stable failed result with `automatic_retry_allowed=false`, and skips reply done feedback. Durable sent records retain the exact source descriptor for producer `read`, while their bounded LICC media summary contains only type/filename/size, never local paths or provider keys. Focused coverage lives in `tests/test_feishu_rich_outbound.py` and `tests/test_feishu_rich_outbound_media.py`.
- **Feishu interactive cards and callbacks:** the strict outbound union accepts complete schema-2.0 cards for `send`/`reply`, and `edit` routes card replacement through the SDK's native card-update API while keeping the exact card JSON in the logical sent record. Visible-text previews deliberately skip callback values. The account consumes the SDK's pre-safety raw card event so repeated intentional clicks on the same button are not collapsed by the SDK's action-identity cache, then applies actor presence and `allowed_users` admission. `FeishuManager` serializes authorized business callbacks by account/chat, durably deduplicates on the raw Feishu event id, stores a `card_action` record with source-message linkage and the raw envelope in the original conversation, and emits a waking LICC update. Callback compound ids are event records rather than reply targets; `read` exposes the exact source card ref for update-or-send handling. Focused coverage lives in `tests/test_feishu_interactive_cards.py`.
- **Feishu localized local-command cards:** after account allowlist and DM/group-mention admission, `FeishuManager` intercepts the nine shared local commands before inbox persistence or LICC wake. `control_cards.py` renders `agent.language`-selected `zh`/`en`/`wen` schema-2.0 cards (unknown language falls back to English), including kanban/system drill-down and local signal feedback. Internal button values are strictly namespaced, update the exact source control card, serialize with business callbacks, and claim a bounded hash of the stable Feishu event id before execution; they never become business `card_action` records. Feishu owns Agent-wide `taskcard.json` settings, while exact resident targets keep their account+chat+thread ownership. Coverage lives in `tests/test_feishu_control_cards.py`.
- **Feishu native progress feedback:** incoming messages retain the established `OK` seen reaction and now use Feishu's transient `Typing` reaction instead of sending/deleting a synthetic “typing” text message; the exact reaction id is kept in memory for best-effort removal when the first response or progress card is sent, while reply completion still adds `THUMBSUP`. `send(placeholder=true)` wraps strict text/Markdown/post phase content in a native schema-2.0 progress card, and subsequent `edit` calls on that persisted placeholder continue to route through native card update while preserving `status='placeholder'`. The tool response and manual require meaningful phase-only edits and a separate durable `send`/`reply` for the final answer; this is phase feedback, not kernel token streaming. Focused coverage lives in `tests/test_feishu_native_progress.py`.
- **Feishu public reactions and classified failures:** `react` is a strict action whose add branch accepts only `message_id + operation='add' + emoji_type` and returns Feishu's provider `reaction_id`; its remove branch accepts only `message_id + operation='remove' + reaction_id`. Both call the generated REST client exactly once. `feishu/_errors.py` normalizes every public action failure to `status/error/message/error_code/retryable/retry_after_seconds`, preserves SDK `SendError` classifications and REST `Retry-After`, and locally classifies reaction code `99992354` as non-retryable `TARGET_REVOKED` until SDK 1.x recognizes it. Channel SDK outbound remains configured with `max_attempts=1`, so `retryable` is caller guidance rather than an implicit replay. Focused coverage lives in `tests/test_feishu_reactions_errors.py`.
- **Telegram public tool surface:** `telegram/server.py` now advertises exactly one public family in stable order: `telegram`. The public programmable Task Card family moved out of MCP ownership and into the intrinsic tools layer. Under official SDK v2 the low-level `Server` still validates only the typed MCP request envelope, not the advertised per-tool `input_schema`, so the handler remains the gate for per-tool argument semantics on the public `telegram` family.
- **Telegram inbound media absolute path + vision hint:** `TelegramManager._download_media` (`telegram/manager.py:1445-1521`) saves inbound photo/document/voice/audio attachments under `<workdir>/telegram/<alias>/inbox/<msg_id>/attachments/` and projects `media` with `type`, `filename`, `path` (absolute local path), `size` (plus `duration`/`mime_type` for voice/audio). A failed document download keeps `type` + document metadata (`file_name`/`file_size`/`file_id`/`file_unique_id`/`mime_type`) with a `download_error` reason and no `path`. The structured per-message render (`telegram/manager.py:1763-1777`) copies the non-None subset of `type`/`filename`/`path`/`size`/`duration`/`mime_type` into `item.media`, and sets `view_with_vision: true` when `path` is present and `type` is `photo`, `document`, or `image` — an explicit hint that the agent should open the attachment with the vision capability instead of treating it as an opaque filename.
- **Automatic Task Card: shared pure projection, channel-owned journal tails and broadcast.** The automatic slot is a bounded, mechanical broadcast of the agent's own behavior, not a per-chat/per-route view or a BaseAgent-owned lifecycle model. Telegram and Feishu each own one lifecycle-bound tail worker for the same authoritative `logs/events.jsonl`; neither writes a durable cursor. Both rehydrate a bounded latest window, leave an unterminated writer tail unconsumed, read later complete appends from a byte offset, and rehydrate after proven truncation/replacement. `TaskCardEventProjection` remains the only safe-event/grouping/redaction/budget/render core. Telegram broadcasts its frame to persisted account+chat residents. Feishu's `task_card.py` broadcasts the same automatic frame to exact persisted account+chat+thread residents, sends topic cards by replying to that route's observed anchor, and keeps last-message ordering state ephemeral so a restart edits conservatively rather than guessing a rotation. Feishu manager lifecycle starts/stops the WS service, automatic journal, then programmable poller in that order. Coverage: `tests/test_task_card_event_projection_shared.py`, `tests/test_telegram_task_card_event_tail.py`, and `tests/test_feishu_automatic_task_cards.py`.
- **Tracked resident Task Card target: shared state machine, provider-owned transports.** `TaskCardResident` takes one stable route lock across automatic and programmable callers, composes the proposed slot with the last committed peer slot, re-reads the tracked resident inside the transaction, and commits the slot only after transport success. Its route supports `account + chat + optional thread`; Telegram uses account+chat while Feishu also binds topic/thread routes. Each adapter supplies exact compound-ID binding, durable/in-memory resident reconciliation, conservative last-message supersession, edit/delete/send, and persistence. The shared state machine edits in place when safe, treats identical provider edits as success through the adapter classification, and rotates old-first only on deterministic supersession or provider-confirmed edit-impossible state. It probes the committed render when available, requires exact-old delete/missing confirmation, adopts a peer's newer resident before sending, and preserves the existing `stale_delete_failed`, `old_resident_deleted`, `indeterminate_send`, and `resident_persist_failed` outcomes. Unknown historical orphan cards remain out of scope. Coverage: `tests/test_task_card_resident_shared.py`, the Telegram singleton/in-place/last-message suites, and Feishu resident suites.
- **Task Card render: shared byte-compatible rows, dynamic footer, bounded metadata, render-time "Last Updated" line.** `TaskCardEventProjection.format_task_card_text()` owns the transport-free row renderer; Telegram's established private formatter methods remain compatibility wrappers and preserve the prior byte surface. One line is emitted per tool call (`tool.action`, redacted reasoning, whole-second elapsed, `✓` when done) with its own inline `started_at` suffix. Malformed/missing `started_at` degrades to no suffix rather than raising. The final standalone line is always `最后更新: HH:MM:SS U±H`, sourced from the render instant and injectable via `now` for deterministic tests. Redaction runs before excerpting, and every row stays represented. The 3500-character budget shrinks reasoning excerpts only; fixed row scaffolding can still exceed it. The footer retains the live `/taskcard N` setting, followed by at most two metadata lines / 150 characters. Telegram's automatic rows still originate from its event-tail worker; neither the shared core nor BaseAgent owns tail lifecycle, routes, or delivery. Byte compatibility is pinned by `tests/test_task_card_event_projection_shared.py` plus the existing Telegram Task Card suite.
- **Resident card, two fully independent composed slots — `automatic` + `programmable`.** The shared resident core stores and composes two independent slots per route; updating one never reads, advances, or overwrites the other's producer state. Telegram and Feishu both read the intrinsic programmable artifact from `<workdir>/taskcard/` without writing it. Missing/invalid/blank producer state preserves each route's last committed programmable slot; exact `inactive` excludes only programmable content. Both adapters skip identical frames and isolate one route's transport failure from all other routes. With both slots present the programmable block remains under `— TASK CARD —`. The retained Telegram controller/interface files remain historical compatibility/projection documentation; the authoritative model-facing owner is `src/lingtai/tools/task_card/`. Feishu coverage lives in `tests/test_feishu_programmable_task_cards.py`.
