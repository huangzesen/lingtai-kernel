# lingtai.kernel

> **Maintenance:** see the `lingtai-kernel-anatomy` skill. **Coding agents** update this file in the same commit as code changes. **LingTai agents** report drift as issues/mail/PR proposals; do not silently fix.

The minimal agent runtime: turn loop, lifecycle, signal consumption, tool dispatch, intrinsic wiring, mailbox glue, soul/molt orchestration. The kernel is standalone — the wrapper package `lingtai` (at `src/lingtai/`) depends on it strictly one-directionally.

> **What is an `ANATOMY.md`?** See the canonical convention at `src/lingtai/intrinsic_skills/lingtai-kernel-anatomy/SKILL.md`. This file follows the same 6-section template as every other anatomy in the tree.

## Components

The kernel root holds the coordinator (`base_agent/`) plus a flat collection of supporting modules. Most are self-contained leaves; subfolders are concept-boundary units with their own anatomy.

- `base_agent/` — `BaseAgent`, the kernel coordinator (package of 7 modules). `base_agent/__init__.py` defines `BaseAgent` (lines 330–3228; 2,899 lines: constructor, properties, state machine, hooks, cross-cutting stubs including the `.notification/` sync trio, pass-throughs to submodules). Submodules: `lifecycle.py` (public typed fail-closed stop proof plus start/heartbeat/signals/refresh — heartbeat tick now also applies the hidden fixed 24h IDLE→ASLEEP timeout before `_sync_notifications`; terminal refresh relaunch failure writes a bounded `logs/refresh_failed_permanent.json` artifact and a high-priority `.notification/system.json` event), `turn.py` (main loop/message dispatch/AED/response processing), `worker_recovery.py` (WorkerStillRunning poison guard, unfinished-turn artifacts, refresh recovery), `tools.py` (tool schemas/dispatch/registry), `identity.py` (naming/manifest/status), `prompt.py` (system prompt building/flushing), `messaging.py` (mail/notification producers/outbound). Soul-flow domain logic lives in `lingtai/tools/soul/flow.py`. See `base_agent/ANATOMY.md`.
- `turns.py` / `execution_workspace.py` / `turn_events.py` / `turn_permissions.py` / `provider_admission.py` — protocol-neutral inbound turn boundary plus optional constrained-composition provider admission. The first four own correlation, settlement/cancellation, optional workspace metadata, bounded fail-open tool-lifecycle observation, separate fail-closed one-shot permission decisions, containment resolution, and explicit parallel-context capture; `provider_admission.py` owns Core-private root/derived parent types, an in-memory derived handle, and the per-provider-call `GRANTED`/`DENIED`/`INDETERMINATE` decision Port. `BaseAgent.submit_turn` exposes the inbound side; ACP-specific sessions/wire and adapter authentication remain outside Core.
- `puffo_admission_witness.py` — pure, dependency-free half of the Puffo admission-witness feature: `extract_admission_receipt(block)` recognises the `[puffo:model-visible-read:<raw>]` receipt marker on a canonical `ToolResultBlock` (structured dedicated-field fullmatch, else plain-text last-marker; synthesized/`read_inbox`/malformed → `None`) and `admission_binding(id, raw)` derives `sha256(id ‖ 0x00 ‖ raw)`. The turn-scoped settle-point wire-scan that consumes it lives in `base_agent/turn.py`; the reliable committed-fact event and its bus are in `turn_events.py` (`ToolResultsCommittedEvent` / `notify_tool_results_committed`).
- `maintenance/` — explicit, operator-run maintenance reporters. `retention.py` implements the dry-run-only retention report for stale terminal daemon run dirs, old sent-mail copies, opt-in archive mail, rebuildable `logs/log.sqlite`, and read-only high-footprint observations for portal replay, agent logs, and history; it never deletes or rewrites files. See `maintenance/ANATOMY.md`.
- `project/` — Core-owned fresh local Project creation. `__init__.py` owns one request/seed/result flow and the single-operation `ProjectWorkspacePort`; it has no filesystem or wrapper imports. Its filesystem adapter exclusively creates and validates one `.lingtai` seed, while `lingtai-agent project create` composes caller inputs and wrapper preset loading. It never starts an Agent or creates global/runtime/asset state. See `project/ANATOMY.md` and `project/CONTRACT.md`.
- `nudge/` — **per-agent periodic checks** that publish read-only findings through ordinary Notification transport. `__init__.py:run_checks_nonblocking(agent)` is called once per heartbeat tick from `base_agent/lifecycle.py:_heartbeat_loop`; cheap evaluations stay synchronous while one named single-flight owner runs folder/event-journal observations in the background; `effective_policy()` owns the shared `LINGTAI_NUDGE_ENABLED` (default `on`) and `LINGTAI_NUDGE_REPEAT_INTERVAL` (default `24h`) controls, and `record_dismissal()` records mute expiry without treating dismissal as resolution. Each check remains a small `check(agent) -> None`; `kernel_version.py` and `source_drift.py` report facts without product-level UTC/fingerprint cadence, while `goal.py` remains an IDLE-only protected-goal system reminder gated by an in-memory 10-second check cadence. Every emitted entry is self-describing and routes to the environment-variable catalogue. See `nudge/ANATOMY.md`.
- `release_manifest.py` — shared, network-free `lingtai.kernel.release/v1` schema/semantic validator used by the runtime release-manifest consumer and the canonical `scripts/lib/release_manifest.py` script import path; it keeps producer, publisher, and consumer bytes on one strict contract.
- `event_journal/` — Core-owned outbound Port for append-only structured events plus authoritative `JournalPosition` provenance. `BaseAgent` receives this Port; POSIX JSONL/SQLite composition lives outside Core. See `event_journal/ANATOMY.md` (`event_journal/__init__.py:9-26`).
- `mail_transport/` — Core-owned outbound Port for fire-and-forget agent messaging (`MailTransportPort`: `send`/`listen`/`stop`/`address`). `BaseAgent` receives this Port as `mail_service`; the concrete POSIX filesystem mailbox (`PosixFilesystemMailAdapter`) lives outside Core and is wired by the CLI. See `mail_transport/ANATOMY.md` and `mail_transport/CONTRACT.md` (`mail_transport/__init__.py:16-62`).
- `workdir_lease/` — Core-owned outbound Port for the exclusive working-directory lease (`WorkdirLeasePort`: `acquire`/`release`). `BaseAgent` receives this Port as a **required** `workdir_lease` (no unlocked/no-op fallback), acquires it once with a 10s grace at construction, and releases it at teardown; the SQLite rebuild receives one too. The concrete POSIX `flock` adapter (`PosixWorkdirLeaseAdapter`) and the fail-loud platform selector live outside Core and are wired by the wrapper/CLI. Read-only lock observers (maintenance/doctor) inspect lock state without acquiring this lease. See `workdir_lease/ANATOMY.md` and `workdir_lease/CONTRACT.md` (`workdir_lease/__init__.py:15-46`).
- `refresh_watcher/` — Core-owned refresh hand-off and watcher-policy boundary. `RefreshWatcherPort.spawn_detached` and immutable `RefreshWatcherRequest` preserve the typed handoff and deterministic request wire. Core also owns the watcher-local `RefreshWatcherProcessPort` value objects (`RefreshWatcherProcessHandle`/`RefreshWatcherProcessObservation`) used by the generated policy for observe, liveness, replacement launch, graceful stop, and force stop; the policy chooses those operations while concrete POSIX ownership remains outside Core. `BaseAgent` receives the outer Port as an optional defaulted-`None` dependency so unrelated raw construction remains valid; `_perform_refresh` fails loudly before handshake mutation when a real launch command exists and calls it once after successful ACK. `watcher_program.py` remains a pure renderer for the existing handshake/retry/heartbeat/matcher/redaction/alert policy and receives `PROCESS_MECHANISM` only through the POSIX entrypoint. The outer `RefreshWatcherPort` adapter, watcher-local POSIX process adapter, entrypoint, and fail-loud `select_refresh_watcher` selector live outside Core and are wired by wrapper/CLI composition. See `refresh_watcher/ANATOMY.md`, `refresh_watcher/CONTRACT.md`, and `refresh_watcher/MANUAL.md` (`refresh_watcher/__init__.py`).
- `snapshot/` — Core-owned outbound `SnapshotPort` and `SourceRevisionPort`. Lifecycle uses the former for opt-in workdir capture/maintenance; runtime identity and source drift use the latter for bounded revision queries. The fixed-command POSIX Git adapter lives outside Core. See `snapshot/ANATOMY.md` and `snapshot/CONTRACT.md`.
- `runtime_identity.py` — compact kernel runtime identity helper for durable event logs. `runtime_identity_event_fields(source_revision_port)` returns the top-level `kernel_version` / `kernel_runtime_stamp` fields plus the nested `kernel_runtime` payload; `runtime_identity(source_revision_port)` computes a cached release/dev stamp from package metadata, editable/source checkout detection, and injected tracked-dirty source revision state without importing the wrapper `lingtai` package.
- `_fsutil.py` — shared, stdlib-only filesystem / JSON / JSONL foundation for kernel state writes. It centralizes sibling-temp atomic replacement, JSON encoding defaults, `read_json(default=...)`, append-only JSONL offsets, and UTC timestamp formatting (`_fsutil.py:1-26`, `_fsutil.py:76-271`).
- `notifications.py` — notification Core: channel allowlist/registration, standard agent-bound producer envelope, atomic acknowledgement policy, and current-payload dismiss/stale-conflict policy (`src/lingtai/kernel/notifications.py:122-219`, `src/lingtai/kernel/notifications.py:606-664`, `src/lingtai/kernel/notifications.py:704-788`, `src/lingtai/kernel/notifications.py:923-1341`). A `cleared: false` no-op dismiss result carries a machine-readable `cause` stamped by the exact branch that decides the no-op (#716): `DISMISS_CAUSE_ALREADY_EMPTY` keys on `update.cleared` from the whole-channel compare-update (`src/lingtai/kernel/notifications.py:1149`), `DISMISS_CAUSE_NO_MATCHING_EVENT` keys on the event mutator's `removed == 0` count (`src/lingtai/kernel/notifications.py:1253`); the constants and their derivation contract live at `src/lingtai/kernel/notifications.py:911-920`, stale-version refusals are a separate `status: error` contract and never carry `cause`, and `tests/test_system_dismiss.py` pins the wire literals against the constants. Persistence is used only through `NotificationStorePort`. Hook allowlisting is **per-agent**: `is_channel_allowed`/`validate_allowed_channel` are workdir-scoped (`notifications.py:186-215`) — hook channels mirrored from `.notification/hooks.json` are allowed only for the agent whose workdir registered them, and with `workdir=None` only the static set and `mcp.*` pass. The mirror lives in module state (`_REGISTERED_HOOK_CHANNELS` keyed by workdir, `_HOOK_REGISTRY_SEEDED`, `_HOOK_REGISTRY_STAT`), serialized under `_HOOK_REGISTRY_LOCK`; `sync_hook_registry` re-seeds it whenever the registry's `(mtime_ns, size)` stat changes (cross-process) and marks a workdir seeded only after a successful load (a transient failure is logged as `notification_hook_registry_error`, `phase=...`, and retried on the next sync). The D2 warn-and-flag scan (`flag_unregistered_channel`/`is_present_channel_flagable`, `notifications.py:515-566`) emits a deduped `notification_hook` blocked-channel event per workdir+channel only for present stems that can become channels — skipping kernel-private dotfiles (`.nudge_state.json`), non-`.json` entries, and syntactically invalid stems — and `add`/`edit` clear the dedupe marker so a later re-block can warn again. Consumer-only delay persists one private `.notification/.delay_state.json` record under the native notification mutation lock, suppresses only its live target in `coherent_attention_read` (an ordinary target is omitted; a `daemon` target keeps its payload and raw entry and has only its attention entry masked to `DAEMON_DELAYED_ATTENTION_TOKEN`, `src/lingtai/kernel/notifications.py:911`), and live-reads `LINGTAI_NOTIFICATION_DELAY_MAX_SECONDS` (default 600) at each delay action; invalid/non-positive configured values log a finite fallback. Expiry/recovery re-exposes the target and writes the separate `delay-alarm` mirror without changing any producer file.
- `notification_store/` — required Core-owned `NotificationStorePort`; exactly eight families end with the hook-registry family: read-only `load_hook_manifests`, atomic `update_hook_manifests`, and read-only `stat_hook_registry() -> tuple[int, int] | None` (the cheap `(st_mtime_ns, st_size)` staleness fingerprint used for out-of-band re-seed; the family mirrors the ack-refs families 6/7) (`src/lingtai/kernel/notification_store/__init__.py:115-254`). Its production POSIX adapter is composed outside Core (`src/lingtai/adapters/posix/notification_store.py:69-314`); daemon append routing stays inside the existing typed `compare_update_channel` family and projects `.notification/daemon/<daemon-id>.json` mini-files into one aggregate; the sibling `.notification/daemon.json` is only a derived run/state report. See the paired child Anatomy and Contract.
- `agent_presence/` — required Core-owned `AgentPresenceStorePort` (construction-bound to one working dir; exactly four operations `observe_manifest`/`observe_heartbeat`/`publish_heartbeat`/`withdraw_heartbeat`) plus the typed `ManifestObservation`/`HeartbeatObservation` evidence and pure `is_agent`/`is_human`/`is_alive` liveness policy (`src/lingtai/kernel/agent_presence/__init__.py`). `BaseAgent` receives it as a **required** `agent_presence` dependency and the heartbeat loop publishes / teardown withdraws through it; foreign-address observers build a target-bound adapter per resolved address. Its production POSIX `.agent.json`/`.agent.heartbeat` adapter is composed outside Core (`src/lingtai/adapters/posix/agent_presence.py`); `handshake` keeps only `resolve_address`. The wall value it publishes is now read from the injected lifecycle clock (below). See the paired child Anatomy and Contract.
- `lifecycle_clock/` — required Core-owned `LifecycleClockPort` with exactly two zero-argument readings (`wall_seconds` for persisted/cross-process timestamps and ages, `monotonic_seconds` for process-local elapsed intervals) and no wait/sleep/scheduler operation (`src/lingtai/kernel/lifecycle_clock/__init__.py`). `BaseAgent` receives it as a **required** `lifecycle_clock` dependency bound before its first time sample; state/progress/deferred/event timestamps, the heartbeat value, and status ages read wall while uptime/idle-timeout/AED/snapshot/GC read monotonic. The one portable production adapter `SystemLifecycleClockAdapter` (direct `time.time()`/`time.monotonic()`) lives outside Core at `src/lingtai/adapters/lifecycle_clock.py`, mapped by `src/lingtai/ANATOMY.md` (not POSIX, not a registry). The heartbeat `Event.wait(HEARTBEAT_TICK_SECONDS)` cadence, notification/event IDs, Agent CPR clocks, and the refresh-watcher subprocess clocks are excluded. See the paired child Anatomy and Contract.
- `daemon_dispatch.py` — append-only daemon acceptance membership/order,
  checked tail/full diagnostics, and marker-only recovery primitives. It never
  owns daemon status or performs a legacy backfill/repair.
- `session_stats/` — the Agent Record: one atomic/versioned/redacted live
  personal record per Agent (including avatars), written to
  `system/agent_record.json`. Its daemon block is a bounded background snapshot
  of dispatch-ledger-selected `daemon.json` records (default 1000); no per-run
  `session_stats.json` is written. Presentation consumers (TUI, `/kanban`,
  `/details`, Telegram, Portal) read and curate this record instead of
  independently re-collecting `.status.json`/heartbeat/daemon state. See
  `session_stats/ANATOMY.md` and `session_stats/CONTRACT.md`.
- `agent_session.py` — explicit **runtime-session** and **agent-session** objects (`RuntimeSession`, `AgentSession`) plus `rebuild_agent_session_from_events()`. Names the two "session" notions the kernel already tracks implicitly so code stops confusing them (spec: `docs/references/runtime-vs-agent-session-objects.md`). `RuntimeSession` = the current runtime lifecycle segment (fresh empty object per process start / refresh / restart / molt; **no id**; not rebuilt from events; grows no product state). `AgentSession` = the agent mind segment keyed by `molt_count` (**no new id**), whose since-molt token aggregate (`api_calls`/`input_tokens`/`cached_tokens`/`output_tokens`, derived `cache_miss_tokens`/`cache_rate`) matches the injected `token_usage.session` shape. `rebuild_agent_session_from_events(agent_dir, molt_count=...)` rebuilds the current agent session from the durable trajectory via a three-tier optimized path — **Tier 1** indexed `log.sqlite` queries (latest `psyche_molt` boundary, then `SUM` of `llm_response` token fields since it; no scan), **Tier 2** bounded reverse/tail scan of `events.jsonl` back to the current molt boundary (sidecar absent/stale), **Tier 3** full forward scan (explicit last resort, logs `agent_session_rebuild_fullscan`) — so the normal case never full-scans a large events file (benchmarked by the `lingtai-kernel-anatomy` skill's `scripts/bench_agent_session_rebuild.py`). `SessionManager` owns both objects (`runtime_session()`/`reset_runtime_session()`, `agent_session()`/`install_agent_session()`), and `BaseAgent.rebuild_agent_session()` drives the rebuild+install at startup.
- `session.py` — `SessionManager`. LLM session lifecycle, token bookkeeping, chat history persistence, AED (auto-error-recovery) retry path. `send()` owns prompt/tool refresh, health checks, LLM dispatch, and usage accounting; it records prompt/schema/provider timing fields before `_track_usage()` logs `llm_response` token fields plus `usage_track_ms` and the filtered allowlisted safe Codex `usage_extra` subset (`session.py:203-267`, `session.py:310-395`); the `llm_call` event additionally carries the frozen provider reasoning decision as six bounded non-secret fields (`provider`, `wire`, `effort_requested`, `effort_normalized`, `effort_emitted`, `effort_provenance`) when available (`session.py:67-92`), plus a non-secret `codex_pool` source-attribution dict when the chat was built by the `codex-pool` factory (`session.py:349-362`, see `src/lingtai/llm/ANATOMY.md`). `_track_usage()` also records the fresh provider round's context pressure via `note_context_pressure_round(input_tokens / context_window, round_id=_api_calls)` for the sustained-pressure streak (channel B) — it uses the **provider-reported** `response.usage.input_tokens` (NOT `get_context_pressure()`'s local-estimate-primary value) so the streak shares the same provider-input ruler as the 0.85 high-context threshold. The streak state machine, warn decision, and reminder prose live in the unified `ContextPressureReminder` abstraction (`reminders/context_pressure.py`, see `reminders/ANATOMY.md`); `SessionManager` constructs one per session (`self._context_pressure`) and keeps `context_pressure_streak` / `context_pressure_warning_active` / `note_context_pressure_round` (plus the new `context_pressure_reminder` accessor) as thin compatibility shims delegating to it. The `_api_calls` round_id dedups multiple meta builds in one batch; `context_pressure_warning_active` (`>= CONTEXT_PRESSURE_WARN_AFTER_ROUNDS` consecutive rounds `>= 0.85`) drives `meta_block.build_molt_context`. The streak is transient (not persisted). Notification delivery stays in `BaseAgent._sync_notifications` so session sends never mutate unrelated tool-result content. It also owns the explicit **runtime-session / agent-session** objects (see `agent_session.py`): a `RuntimeSession` re-minted at every runtime boundary inside `reset_runtime_session_token_usage()` (so the named object follows the same `_session_baseline_*` boundary as the since-refresh deltas), and an installed `AgentSession` (`install_agent_session()`/`agent_session()`) whose since-molt numbers are surfaced by `agent_session_token_usage()` — the view `meta_block._build_session_token_economy` consumes for the injected `token_usage.session` half. `agent_session_token_usage()` reads the same cumulative `_total_*`/`_api_calls` counters as `get_token_usage()`, so it stays correct as live provider rounds accrue after a startup rebuild. It ALSO owns the process-local **runtime reasoning-effort controller** (`self._reasoning_effort`, a `llm/reasoning_effort.ReasoningEffortController` — see `src/lingtai/kernel/llm/ANATOMY.md`): `_bind_reasoning_effort(chat)` runs at every session-assignment site (`ensure_session`, `_rebuild_session`, and the `chat` setter) so an in-process rebuild keeps the override and rebinds the snapshot callback, and it binds through the `set_reasoning_effort_policy` METHOD rather than an attribute write so the rate-gate session proxy cannot swallow it. `reasoning_effort_status()` / `set_reasoning_effort()` / `clear_reasoning_effort()` / `last_reasoning_effort_dispatch()` are the self-facing entry points (`BaseAgent` delegates the first three verbatim). The controller is deliberately transient: it survives an in-process rebuild and NOT a process refresh/restart/molt/suspend. `_SAFE_USAGE_EXTRA_EVENT_KEYS` additionally allowlists `codex_reasoning_effort` / `codex_reasoning_effort_source` / `codex_reasoning_effort_revision` for `events.jsonl`.

## Notifications — the `.notification/` filesystem-as-protocol

> **Contract:** changes to LICC/MCP notification event identity, `.notification` envelopes, `_meta.agent_meta.notifications.attention`, `_meta.agent_meta.notifications.persistent`, or producer read/dismiss authority must check `src/lingtai/services/LICC_NOTIFICATION_CONTRACT.md` in the same change. The contract names the attention/context/authority split and its review-trigger paths.

Out-of-band events — mail arrival, soul-flow firings, daemon emanations, MCP webhook events, kernel-internal alerts — surface as one **live notification payload holder** at a time. When the agent is IDLE/ASLEEP, the holder is a synthetic `(ToolCallBlock, ToolResultBlock)` pair of shape `notification(action="check")` whose result carries the canonical JSON union of all currently-active producer files. When the agent is ACTIVE and has just produced an ordinary final ToolResultBlock, the holder is the same canonical `_meta.agent_meta.notifications.attention` + `_meta.agent_meta.guidance.transient` payload — but on every eligible ACTIVE final result, including when unchanged (`meta_block.attach_active_notifications`, `base_agent/turn.py`). When a newer holder takes over, the old holder — synthesized or a normal tool result — is simply released from live tracking; its recorded content is never mutated, so it remains in canonical history exactly as sent (append-only — see `meta_block.skeletonize_notification_holder`).

```
assistant: tool_call(id=notif_…, name="notification", args={action:"check"})
user:      tool_result(id=notif_…, synthesized=True, content="""{
             "_synthesized": true,
             "_meta": {
               "agent_meta": {
                 "guidance": { "transient": "…kernel safety framing…" },
                 "notifications": { "attention": {
                 "email":  { "header": "3 unread emails", "icon": "📧", ... },
                 "soul":   { "header": "soul flow",       "icon": "🌊", ... },
                 "system": { "header": "2 system notifications", "icon": "🔔",
                             "data": { "events": [...] } }
                 }}
             }
           }""")
```

- Each actual-block injection also records a durable `notification_block_injected` event with `mode`, `call_id`, `sources`, and the full persisted `_meta` envelope (`tool_meta`, `agent_meta`, `agent_meta.guidance`, `agent_meta.notifications.attention`, `agent_meta.guidance.transient`) so `/notification` can replay the same metadata shape the model saw live (`base_agent/__init__.py:1563`, `base_agent/turn.py:1574`).

- Each synthesized pair also writes a durable synthetic `tool_result` recovery record (`origin="kernel_notification_sync"`, `result_metadata`, `synthesized=true`, deterministic `redacted` flag) that `tool_result_recovery.py` replays origin-gated during heal, so a provider/WS rollback does not lose the notification envelope; a `redacted=true` replay is marked `_meta.redacted` and resets the committed fingerprint (`notification_redacted_replay_resync`). Normative contract: `src/lingtai/services/LICC_NOTIFICATION_CONTRACT.md` ("Synthetic pair durability and heal replay").

### Communication responsiveness

Notification previews deliberately trade completeness for latency: they let the agent notice that something arrived, not necessarily act safely from the preview alone. The operational rule lives in the substrate: answer directly only when the newest human message is complete and unambiguous; otherwise read the producer with the normal top-level channel tool before doing long work. If a human is waiting and the next step may take time, acknowledge or reply through the communication tool directly before starting the long-running tool. The kernel no longer provides a reserved nested communication side channel; tool execution now stays aligned with provider/top-level tool calls.

| `goal.json` | active-goal source of truth (protected from generic dismiss) | bare intrinsic name |
| `mcp.<server>.json` | external MCP server adapter (e.g. `mcp.imap.json`, `mcp.telegram.json`) | dotted prefix |

Each file is the producer's complete state for that channel — there is no "queue of unread events." When the producer's state empties (e.g. unread count drops to 0), it deletes the file. The basename (without `.json`) becomes the dict key the agent sees in `notifications`.

The reader path is allowlist-based. Built-in channels, the dynamic `mcp.*` prefix, and this agent's own registered hook channels (mirrored per workdir from `.notification/hooks.json`) are visible; unknown `.notification/*.json` files are ignored by fingerprinting/collection and cannot be mutated through kernel publish/clear/dismiss helpers. This prevents accidental prompt injection from arbitrary files in the notification directory while preserving MCP server fan-out.

### Single-LIVE-holder invariant (timely transient, latest-only)

At most ONE holder is tracked as the LIVE notification payload at any time, recorded as `agent._notification_live_holder` (`base_agent/__init__.py:489`) — either a synthesized notification result dict or a normal tool-result content dict. When payload moves, `meta_block.skeletonize_notification_holder` (`meta_block.py`) releases the old holder from live tracking without mutating it: both a synthesized pair and a normal tool result **retain** their recorded `_meta.agent_meta.notifications.attention`/_meta.agent_meta.guidance.transient` content unchanged as a historical trace — canonical history is never retroactively stripped or rewritten (Jason #4307). The payload is timely transient state: when several copies appear in historical context or logs, only the newest emission is current; older copies are past state, not unhandled instructions. Model-facing full-history serialization — the shared converters in `lingtai/llm/interface_converters.py` used by every adapter's full replay — do not strip these keys from any historical holder, without rewriting recorded history; the ONLY historical tool-result body replacement a rebuild applies is `summarize`. Only the latest holder per family represents current state — older holders remain visible in replay as historical traces and must not be acted on. The complete newest `_meta.agent_meta` snapshot is emitted whenever private capture exists; prior snapshots remain unchanged historical traces and only the newest is current/actionable. Agents act on the **current** notification state; past arrivals belong in the producer's own logs (e.g. `mailbox/inbox/`, `logs/soul_flow.jsonl`).

### Producer contract — `submit(agent, tool_name, *, data, header, icon, priority, instructions=None)`

In-process producers call **`publish_notification`** (re-exported by the `system` intrinsic from `notifications.submit`) — the strict agent-bound helper that publishes the standard envelope through the injected Store:

```python
from lingtai.kernel.notifications import submit as publish_notification, clear as clear_notification

publish_notification(
    agent, "email",
    header=f"{n} unread email{'s' if n != 1 else ''}",
    icon="📧",
    instructions=(
        "After handling, call email(action=\"read\", "
        "input={\"email_id\": [...]}, reasoning=\"Read this email.\") "
        "or email(action=\"dismiss\", input={\"email_id\": [...]}, "
        "reasoning=\"Dismiss handled email.\") to clear handled mails "
        "from this notification."
    ),
    data={"count": n, "newest_received_at": ts, "email_ids": ids, "emails": emails},
)

# When state empties:
clear_notification(agent, "email")
```

Side effects of `publish_notification`:
- Writes `.notification/<tool_name>.json` atomically (tmp + rename) with `{header, icon, priority, published_at, data}` plus an optional top-level `instructions` field when the producer supplies one.
- Returns immediately — no enqueue, no wake post. The kernel sync mechanism (next section) handles wire injection.

The optional `instructions` field is the producer-side directive — text describing what the agent must do to dismiss or act on the notification. It rides with the payload so each producer owns its own dismissal contract; generic frontend / kernel code does not need to know per-producer rules. Email uses it for "call read or dismiss to clear"; soul flow sets it to advise that voices are inner monologue (no dismissal needed); MCP servers can carry their own. Separately from `instructions`, the kernel injects a compact `_meta.agent_meta.guidance.transient` ref/hook pointing to resident `meta_guidance.notification_handling`; per-source payloads under `_meta.agent_meta.notifications.attention` no longer repeat kernel-side safety prose. That safety framing is about source provenance and verification, not a producer dismissal contract.

**Dismissal contract.** Producers fall into four categories. **Category A — mirror over real producer state** (e.g. `email` over `read.json`) MUST register with `register_generic_dismiss_guard("<channel>", "<suggested verb>")`; generic clearing would leave producer state unchanged and the mirror inaccurate. **Category B — notification IS the output** (e.g. `soul`) may use `notification(action="dismiss_channel", input={"channel": ..., "force": null, "reason": null}, reasoning=...)` after handling. **Category C — coalesced event summary** (e.g. `mcp.<server>`) may use the same atomic channel dismissal after the agent has handled the summarized event. **Category D — protected source of truth** (currently `goal`) is allowlisted but refuses generic dismissal even with `force`; cancel or complete it through the goal manual instead of mutating the notification file directly. The `system` channel is Category B with two targeted paths: `notification(action="dismiss_event", input={"event_id": ..., ...}, reasoning=...)` removes one matching entry, while `notification(action="dismiss_ref", input={"ref_id": ..., ...}, reasoning=...)` removes matching producer refs; each preserves the file when other events remain. New producers declare the category and follow that contract.

External producers (MCP servers over SSH, separate processes) bypass the helper and write the same envelope directly to `<workdir>/.notification/mcp.<server>.json` using `tmp + rename`. The contract is the filesystem layout, not the Python API.

### Sync mechanism — `BaseAgent._sync_notifications`

Five pieces of state on `BaseAgent` (`base_agent/__init__.py:457-489`):
- `_notification_fp: tuple` — last successfully observed **attention** fingerprint; updated only after a successful snapshot/sync decision. This is the Store fingerprint masked by `notifications.coherent_attention_read`: when `<agent>/notification.json` sets `channels.daemon.alarm_threshold`, the synthetic aggregate daemon entry's content hash is replaced by a token derived only from `data.daemon` alarm state, so below-threshold daemon arrivals stay readable through snapshot/check without moving this value (no wake, no injection) while the strict `count > N` crossing moves it exactly once. Absent a valid threshold the raw hash passes through, unless a live consumer `delay` targets the daemon channel: that masks the same entry to the constant `daemon:delayed=1` for its bounded window, so daemon arrivals stay readable without waking. Every comparison against this field — `_sync_notifications_locked`, `meta_block._commit_notification_fp`, the IDLE boundary check in `turn.py`, `soul/flow.py`, and the `karma.py` sleep guard — must use the same masked value, or a raw/masked mismatch would wake the agent the mask exists to keep quiet. The `()` an agent starts at is *not* this baseline when a threshold is configured: `notifications.masked_empty_attention_fp` resolves the empty baseline through the same mask (the virtual quiet `daemon.json` token), so an agent first seeing a sub-threshold file stays silent while an alarmed first write — threshold `0`, or a payload already past `count > N`, whose token is `daemon:alarm=1` — still wakes.
- `_notification_raw_fp: tuple` — the same fingerprint BEFORE daemon-attention masking, committed alongside `_notification_fp` from the *same* coherent observation (and reset together on molt/redacted-replay resync). Two consumers: (1) `notifications.dismiss_channel`'s non-forced optimistic-concurrency check sources its `delivered` CAS token from this field, never from the masked one — `compare_update_channel` always compares the Store's real `(name, size, sha256)` triple, which the masked daemon token (`("daemon.json", 0, "daemon:alarm=0")`) can never equal; sourcing CAS from the masked value would make every non-forced dismiss of a threshold-masked channel refuse as stale. Because the committed value comes from the observation the delivered payload was built from, this token always describes the bytes the model actually received — a producer publishing between delivery and commit can no longer have its undelivered payload cleared by a non-forced dismiss. (2) `_sync_notifications_locked`'s early-return: when the masked fingerprint is unchanged (no wake-worthy delta) but the raw one moved — e.g. a sub-threshold daemon mini-file was cleared, which the mask's virtual quiet entry hides from the masked comparison — a live holder still advertising the removed state is skeletonized without injecting or posting a wake. That release is gated on holder liveness, not on the whole snapshot being empty, so it also fires when another channel (`email`) keeps the snapshot non-empty; `_notification_raw_fp` is committed only *after* the release runs, so a poisoned interface or an unstable read retries on the next tick instead of permanently consuming the clear.

`notifications.coherent_attention_read` is the single read seam behind both fields. The Store Port exposes no atomic snapshot-plus-version primitive (`fingerprint()` and `snapshot()` are independent unlocked reads), so it composes them with verify-and-retry — fingerprint, snapshot, fingerprint again — and returns a `CoherentAttentionRead(raw_fp, masked_fp, payloads, stable)` whose three values describe one instant. This is what lets the delivered payload and its CAS version agree, and what stops a torn read from pairing an alarmed `daemon.json` hash with a post-clear payload (which would rewrite the alarmed entry to the quiet token and drop the crossing with no file left to replay it). `stable=False` means a producer was writing throughout the read; callers treat it as "state is moving", never as evidence of quiet.
- `_notification_block_id: str | None` — informational `call_id` of the latest injected synthesized pair; retained for molt/reset telemetry, no longer used to delete pairs.
- `_notification_inject_seq: int` — monotonic injection counter so repeated notification payloads still produce unique synthetic pairs.
- `_notification_live_holder: dict | None` — the single current dict tracked as the live notification payload; released whenever payload moves, both for a synthesized pair and a normal result — release never mutates the holder, so it keeps its recorded payload as a historical trace.

The sync loop runs from **two trigger points**:
1. **Heartbeat tick** (`base_agent/lifecycle.py:486`) — `agent._sync_notifications()` after `_check_rules_file`. Default cadence is the heartbeat interval (~1s); the producer's `_wake_nap` calls also nudge the heartbeat for sub-second latency.
2. **Voluntary calls** — `notification(action="check")` (`lingtai/tools/notification/__init__.py`) returns a placeholder dict (`_notification_placeholder: True` + explanatory message); the canonical `_meta.agent_meta.notifications.attention` + `_meta.agent_meta.guidance.transient` keys are stamped onto that same result by the ACTIVE-path `attach_active_notifications` post-hook, just like any other final tool result. There is no separate "voluntary returns bare channel keys" code path — notifications surface only via the meta-block path so at most one notification payload is tracked as current/actionable at a time; older copies remain historical traces.

`_sync_notifications` (`src/lingtai/kernel/base_agent/__init__.py:1290-1564`):
1. Seed the hook-channel mirror (`sync_hook_registry`), then take ONE
   allow-all Store fingerprint and derive the allow-filtered view from it — a
   single hash pass per tick in steady state. If the allow-filtered fingerprint
   is unchanged, return (cheap path — the common case). Whenever the allow-all
   view changed (cached as `_notification_present_fp`), the D2 warn-and-flag
   scan flags present-but-unregistered channel stems that can become channels
   (skipping kernel-private dotfiles like `.nudge_state.json`, non-`.json`
   entries, and syntactically invalid stems) with a deduped `notification_hook`
   blocked-channel event per workdir+channel.
2. On change, obtain the current allowlisted Store snapshot. If empty, release the live holder (without mutating it), commit the empty fingerprint, and return.
3. Otherwise, keep the old live holder intact until a new holder is successfully registered; this preserves the only live payload if injection is blocked by pending tool calls.
4. Otherwise, dispatch on agent state:
   - **IDLE** — `_inject_notification_pair` splices the synthetic `(ToolCallBlock, ToolResultBlock)` pair (impersonating a voluntary `notification(action="check")` call from the agent's perspective), then posts `MSG_TC_WAKE` and `_wake_nap("notification_sync")`. IDLE is "blocked on `inbox.get()`," so without a wake the loop sits forever and the pair never reaches the LLM. **Wake handler**: `_handle_tc_wake` (post-redesign) drives one inference round off the existing wire via `session.send(None)` — the adapter skips the input-append step and sends the canonical interface as-is. From the LLM's viewpoint the wake is indistinguishable from the agent voluntarily calling `notification(action="check")` and reacting to the result. No fake user message, no meta prefix. (The earlier wake-message draft posted `MSG_REQUEST(content=None)` to drive a meta-only turn through `_handle_request`; that was reverted because the meta line landed visibly in the agent's chat history every time a notification arrived. The "voluntary call" framing is cleaner.)
   - **ACTIVE** — after each tool-result batch, `attach_active_notifications` attaches the canonical payload nested under `_meta.agent_meta` to the final carrier on every eligible batch; the fingerprint is delivery bookkeeping and does not gate the snapshot (`base_agent/turn.py`, `meta_block.py`). If the batch has no dict result, the old holder stays live and the fingerprint remains uncommitted so IDLE delivery can retry later. **Post-molt special case:** `psyche(action='context_molt', ...)` publishes `.notification/post-molt.json` before its own tool result returns, so that same result batch deliberately skips ACTIVE notification stamping/fingerprint commit (`base_agent/turn.py:936-956` detect the molt batch; `base_agent/turn.py:1508-1517` release-only/skip-stamp branch). This leaves the just-written post-molt state for the next boundary: if the agent becomes IDLE/ASLEEP, `_sync_notifications` injects the synthesized pair + `MSG_TC_WAKE`; if the agent continues ACTIVE, the next non-molt tool-result batch may consume/stamp the post-molt notification normally. The bug was the old behavior where the molt result itself stamped + fingerprinted post-molt, making the next IDLE pass see no change and never wake.
   - **ASLEEP** — clear `_asleep` while preserving `_cancel_event`, transition `IDLE` (reason `notification_arrival`), `_reset_uptime`, then proceed exactly like the IDLE branch (inject pair + post `MSG_TC_WAKE` → `_handle_tc_wake` drives the wire). The next successful fresh inbox dequeue consumes any stale cancellation latch after rechecking shutdown and before publishing or merging the request. This is the canonical notification-driven wake. **Degraded fallback:** if `_inject_notification_pair` still returns False after `_heal_pending_tool_calls` (a wire shape heal cannot rescue), stay IDLE, enqueue one `MSG_REQUEST` from `system` naming the affected sources and pointing the agent at `notification(action="check")` or direct `.notification/` reads, log `notification_wake_degraded`, and commit the fingerprint so the failure does not replay until on-disk state changes. Reverting to ASLEEP without committing the fingerprint produced a livelock (heartbeat → wake → inject fail → revert → repeat); the degraded fallback unblocks the run loop instead.
   - **STUCK / SUSPENDED** — observe but don't inject. The on-disk state is captured; injection is deferred until state recovers.
5. Commit the new fingerprint **only if** a live holder was successfully updated (synthesized pair injected or canonical payload stamped onto a tool result), the state is empty / cannot inject (STUCK / SUSPENDED), or the ASLEEP degraded fallback fired (see ASLEEP bullet above — committing here is what breaks the heartbeat replay loop). If `_inject_notification_pair` returned False because `interface.has_pending_tool_calls()` (mid-pair tail), if ACTIVE stamping found no final tool result, or if the active batch was the `psyche(action='context_molt', ...)` batch that just published `post-molt.json`, `_notification_fp` stays at its prior value and the next tick/boundary retries. Ordinary ACTIVE stamping commits the full current notification fingerprint for the payload it just attached.

### Why this beats the legacy `tc_inbox` queue

The previous design (queue of `InvoluntaryToolCall` items + pre-request drain hook + per-id dismiss path) carried four pain points:
1. **Stateful queue** — producers had to track whether their event was still queued vs already spliced (the `_dismiss` path branched on this).
2. **Per-arrival pairs** — every event got its own pair. A burst of arrivals during ASLEEP woke the agent N times with N pairs to dismiss.
3. **Two consumers** — `_drain_tc_inbox` was called from `_handle_request`, the pre-request hook, and `_handle_tc_wake`, with subtle ordering and idempotency requirements.
4. **No external-process producers** — only in-process Python could enqueue; MCP servers running over SSH had no path.

The filesystem-as-protocol redesign collapses all four into "write a file, read a fingerprint." Producers are stateless; agents observe current state, not arrival history; the kernel has one consumer (`_sync_notifications`); and any process that can write to the workdir is a valid producer.

### Voluntary `notification(action="check")` — read-your-mailbox path

Beyond kernel-driven sync, agents can call `notification(action="check")` themselves. The handler (`lingtai/tools/notification/__init__.py`) returns a placeholder dict — `{"_notification_placeholder": True, "message": "…"}` — and never builds the bare channel collection itself. The turn-loop post-hook `attach_active_notifications` then stamps the canonical `_meta.agent_meta.notifications.attention` + `_meta.agent_meta.guidance.transient` payload onto that same result, exactly as it would for any other final tool result. From the agent's perspective this is indistinguishable in shape from a kernel-synthesized pair (which additionally carries `_synthesized: True`). Useful when the agent wants to recheck producers without waiting for the next sync tick — and because the read path is unified with the meta-block stamp, there is never a duplicate representation of the same channels in one result.

### Migration window — `tc_inbox` is dormant, not deleted

Phase 2 (`d2da97e`) migrated all in-tree producers (mail, system events, soul flow) to `publish_notification`. Phase 2.5 migrated the LICC MCP inbox (`core/mcp/inbox.py`) to publish via `notifications.submit` to `.notification/mcp.<server>.json` instead of posting to the legacy inbox queue. The `tc_inbox.py` module survives as dead code — no producer enqueues, the drain hook is still installed but always finds the queue empty. Phase 3 (deferred to a separate point release after soak) will:
- Delete `tc_inbox.py`.
- Remove the pre-request drain hook from `BaseAgent._install_drain_hook` and the three drain call sites.

(The legacy `ids=` soak path on the old `system(action="dismiss")` action no longer exists — #426/#428 split dismiss into the standalone `notification` tool with atomic `dismiss_channel` / `dismiss_event` / `dismiss_ref` actions and removed the agent-callable `system.dismiss` alias entirely, so there is no per-id soak path left to retire.)

### Adjacent: healing mid-pair tails

Distinct primitive (and unrelated to notifications) — `interface.close_pending_tool_calls(reason)` (`llm/interface.py:465`) closes orphan tool calls when the wire chat itself ends mid-pair (process killed mid-turn, snapshot saved mid-turn). It first gives an optional recovery lookup a chance to replay durable results from `logs/events.jsonl` — preserving each recovered block's recorded content, `metadata`, and `synthesized` state (`False` for ordinary executed-tool replays, `True` for replayed kernel-synthesized notification pairs) — then synthesizes `ToolResultBlock(synthesized=True)` placeholders for any remaining misses. If a real result arrives later for the same id, `add_tool_results` overwrites a synthesized placeholder so the wire stays honest. Used in `base_agent/turn.py` after sleep/retry/continuation exceptions, by `SessionManager.restore_chat()`, and by notification wake-heal when an IDLE injection finds a pending tail. The notification path also uses `synthesized=True` for its own injected `(notification(action="check"), result)` pair.

### Historical note: retired ACTIVE meta-prefix injection

Issue #82/#83 retired the ACTIVE-state `notifications:\n<json>\n\n` prefix path. Earlier code stashed notification JSON during ACTIVE and had `SessionManager.send()` prepend it onto the latest `ToolResultBlock`, which polluted unrelated tool output (e.g. daemon dispatch results) and invalidated strict-prefix caches. ACTIVE sync now leaves the fingerprint uncommitted and delivers only after the agent is observably IDLE via the same synthetic pair + `MSG_TC_WAKE` path used for ordinary notification wakeups.

## Two-axis `_meta` boundary

`ToolResultBlock.metadata` is the canonical runtime sidecar. It is serialized
with chat history and projected by every provider converter, so handlers keep
returning strings, dictionaries, or other supported values unchanged. The
model-visible root has only `tool_meta` (immutable execution-local facts) and,
for main-agent tool batches, `agent_meta` with `instruction`, `agent_state`,
`notifications`, and `guidance.persistent`/`guidance.transient`. Token/session/
context/reconstruction state belongs under `agent_state`; notification
attention and persistent communication context belong under `notifications`.
Only the latest agent-meta instruction is current; historical holders remain
physically intact for replay and prefix caching. Daemon wiring uses the shared
`meta_block.attach_daemon_agent_meta` projector for daemon-local runtime,
token, and context state, while intentionally omitting parent notifications and
communication state.
